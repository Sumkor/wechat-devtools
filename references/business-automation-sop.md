# Business Automation SOP

## 状态分层

不要把进程存在、端口监听和业务页可操作视为同一状态：

1. daemon IPC 可用：只说明本 Skill 的 Node daemon 正常运行。
2. 9420 已监听：说明微信开发者工具已开放 Automator WebSocket；daemon 仍可能尚未建立或已经丢失会话。
3. 业务页可操作：说明项目已完成当前阶段的编译，目标页面、组件和数据已经出现。

项目首次编译、切换环境或恢复 IDE 状态时可能需要数分钟。按条件轮询，不使用固定长 sleep；启动状态判断和 daemon 恢复统一见 [diagnostics.md](diagnostics.md)。

## 业务操作顺序

1. 确认当前项目和当前路由：

```shell
node .\scripts\weapp-auto.js session status
node .\scripts\weapp-auto.js page current
```

2. 优先读取项目路由配置，再决定点击还是直接导航。检查 `app.json`、分包 `root/pages`、`tabBar.list`，必要时搜索项目封装的 `navigateTo`、`switchTab` 和目标详情路由。已知路由时，使用官方导航方法通常比逐层猜 selector 更快、更稳定。

3. 执行业务动作后，先读取页面运行时状态。`page.data()` 是官方 Automator 提供的通用 Page `data` 读取能力，但不是网络响应读取能力；能否找到接口数据，取决于业务是否通过 `setData` 或状态映射把目标字段写入 Page `data`。

```shell
node .\scripts\weapp-auto.js page data --path 'result.list'
```

优先读取可能的局部路径；未知结构时再请求受限深度和数量的紧凑 data。不要默认输出完整页面 data 或元素树。

4. 页面 data 没有目标字段时，检查承载列表或业务状态的自定义组件。接口结果可能只写入组件 `data`，此时使用：

```shell
node .\scripts\weapp-auto.js element data --selector '.result-list' --path 'list'
```

若数据只存在于局部变量、闭包、普通实例字段、状态管理库内部、插件、原生组件或 WebView 中，页面和组件 data 都可能读不到；不要因此判断接口没有返回数据。

5. 页面和组件 data 都不足时，搜索项目源码中的请求方法、`setData`、状态映射、响应转换和点击回调，建立“接口字段 -> 运行时状态 -> 路由参数”的映射。接口响应可能已经被裁剪、重命名或分页合并，应以业务实际使用的字段为准。

6. 对搜索、提交、保存、支付前置校验、列表加载和详情加载等关键操作，若会话已启用 CDP，操作前执行 `network clear`，操作后执行 `network wait/list`。请求 URL、状态码、请求参数和响应数据既可用于下一步导航，也应作为自动化失败排查证据。详见 [network-capture.md](network-capture.md)。

7. 页面和组件 data 足够完成操作时，仍可关注关键请求是否成功，但不要无条件读取所有响应体。仅对业务相关 URL 按需调用 `network body`，并限制输出大小。

8. 点击列表项时，优先点击明确绑定事件的图片、标题或内容节点。若源码或关键接口响应已经表明详情路由只依赖 ID，可从页面 data、组件 data、响应体或业务映射中取得首项 ID 后直接导航，避免反复试探容器 selector。

## 提速与减少堵塞

1. 只读取当前任务需要的 reference。启动问题读 `diagnostics.md`，真实业务读本文件，需要抓包时再读 `network-capture.md`；不要为了普通业务任务预读全部 reference。
2. 源码探查先读 `app.json` 和明确目标页面/组件。对编译产物使用精确目录与 `--glob` 排除 `common/vendor.js`、`node_modules` 等大文件，避免全项目宽泛搜索产生截断输出。
3. Windows PowerShell 中不要把 `index.*` 这类通配符作为 `rg` 的路径参数；使用真实目录配合 `-g 'index.*'`，避免无效命令往返。
4. 导航命令已经返回目标路由时，不要无条件再读 `page current`；仅在超时、返回不透明、路由未返回或下一步必须核对时补查。`page stack` 只用于栈异常或返回路径排查。
5. 已知接口 URL 时直接 `network wait --url ...`，不要先执行无筛选 `network list`。只有接口未知、等待超时或存在多个候选请求时再 list。
6. 响应只读取完成任务所需的最小投影。例如只需要列表第一条记录时，优先使用 `network body --json-path 'data.records.0'`，不要读取整个分页响应；仅在需要请求参数或响应头时调用 `network detail`。
7. 每个关键动作只保留一条确认链：`network clear -> 动作 -> route/request -> 最小 data/body -> 最终截图`。同一事实已被路由和目标响应证实时，不再追加重复 data、元素和截图检查。
8. 自定义组件或瀑布流无法稳定穿透时，最多做一次精确 selector 尝试；若源码已证明点击仅拼接 ID 路由，立即改用等价导航，不在组件树中反复试探。
9. 不把多个可能阻塞的 CLI 动作串在同一个 PowerShell 调用中。上一步输出不完整时，先检查实际路由或请求状态，不要整组重放。

推荐的“入口/列表 -> 目标详情”通用流程：

1. 从 `app.json` 确认入口、列表页和详情页路由；若涉及 Tab，先确认 `tabBar.list`。
2. 使用官方导航进入业务入口；源码确认列表页支持等价路由参数后，可带参数进入列表页。
3. 列表加载前 `network clear`，等待已知列表接口，核对关键请求参数，并只读取目标记录所需的最小字段。
4. 源码确认列表项点击的路由参数和业务副作用；能稳定点击则点击，否则以稳定业务 ID 等价导航详情。
5. 详情加载前重新 `network clear`，等待详情请求，只读取单条详情记录所需字段。
6. 最后读取一次当前路由并截图，作为页面已正确渲染的最终证据。

## 重组件页面探查

对包含大量自定义组件、瀑布流、原生组件或复杂渲染树的页面，不要先执行宽泛的整页查询，例如 `query-all input`、`query-all view` 或高上限通配查询。这类操作可能遍历重组件树并长时间占用 daemon 串行队列。

优先按以下顺序缩小范围：

1. 从 `app.json` 的 `tabBar`、分包和页面列表确认目标路由。
2. 搜索目标页面源码中的占位文字、事件绑定、导航 URL、请求常量和查询参数。
3. 使用明确 class、id 或组件 selector 查询单个控件。
4. 只有结构确实未知时才执行受限 `query-all`，并设置小 `limit`；超时后不要立即扩大查询范围。

对于搜索页，若源码确认页面支持 `keyword` 等路由参数，并且 `onLoad` 会触发与输入提交相同的查询逻辑，可通过带参数的官方导航进入搜索结果页。随后必须用 CDP 请求参数确认关键词确实生效，不能只根据路由 query 判断搜索成功。

## 列表目标定位决策

处理瀑布流、虚拟列表、分页列表或自定义组件列表时，按以下顺序定位目标：

1. 在触发列表加载前执行 `network clear`，再用业务关键词筛选列表接口。优先从响应中取得目标记录的稳定标识、标题、发布者和类型，不要只依赖截图逐屏查找。
2. 搜索列表卡片的点击回调和导航代码，确认稳定标识如何转换成详情路由。只有“接口目标记录”和“源码路由参数”相互印证后，才把直接导航视为等价的卡片点击。
3. 若目标当前可见且 selector 可稳定定位，执行真实点击；这更接近用户路径，也能覆盖点击事件中的埋点或前置逻辑。
4. 若卡片位于自定义组件、虚拟列表或动态瀑布流中，先查询承载卡片的组件并读取其紧凑文本或 data。Page 级 selector 不保证穿透自定义组件边界，父页面查不到子组件节点不代表节点不存在。
5. selector 无法稳定穿透，且点击逻辑已确认只负责拼接详情路由时，使用官方 `navigateTo` 进入同一路由。若点击还包含权限校验、状态写入、埋点之外的业务副作用，则不要绕过点击，应继续定位组件实例或补充专用封装。

不要把接口数组下标直接映射为瀑布流列号、DOM 顺序或动态元素 ID。双列布局、异步图片高度、过滤、分页合并和组件内部重排都可能改变视觉顺序。接口的稳定业务 ID 可用于确认目标，下标只能作为线索。

滚动查找时使用分段位置和截图验证，不要凭接口下标猜固定滚动距离。先检查当前可见文本，再按较小步长调整 `scroll-view scrollTo`；出现“没有更多了”时应回退，而不是继续向下滚动。

## 等待与结果确认

- 点击、`navigateTo` 或 `switchTab` 返回成功，不等于新页面已经完成加载。
- Automator 操作返回 `timeout`、`Uncaught [object Object]` 等不透明异常，也不等于动作一定失败；导航、输入或点击可能已经发送到小程序。先再次检查 `page current`、目标元素和关键请求，确认状态后再决定是否重做。
- 使用 `--wait-route`、`page wait` 或短周期轮询确认目标路由/元素，避免点击后立即读取一次就判定失败。
- 路由确认后，再断言标题、关键元素或 data；必要时截图做最终视觉确认。
- 页面异步加载期间保持串行操作，同一实例不要由多个 Agent 或脚本并发控制。

对可能阻塞的 `page wait`、截图、深层 data 读取和通用 `invoke`，一次 CLI 调用只执行一个待确认动作。不要把“导航 -> 长等待 -> 抓包 -> 截图”串成一个外部命令；其中一步超时后，后续步骤无法区分是未执行还是仍在 daemon 队列中。推荐拆成：

1. 清空抓包并执行动作。
2. 单独轮询 `page current` 或短超时 `page wait`。
3. 单独读取关键请求和有限 data。
4. 最后截图确认。

客户端命令超时不保证 daemon 中的请求已经取消。若后续所有 CLI 调用持续排队或超时，先确认没有其它 Agent 操作，再停止本 Skill 的 daemon、清理残留的本 Skill CLI 进程，并用 `session start --project ...` 复用现有 9420 会话。不要因此重启或重复打开微信开发者工具；重连后先读取 `page current`，动作可能实际上已经完成。

推荐确认顺序：目标路由 -> 关键 data/元素 -> 截图。若路由已经变化但内容仍为空，继续等待编译或接口数据，不要重复点击导致二次导航。

## 快速恢复

1. 当前路由异常：读取 `page stack`，根据 `app.json` 使用 `switchTab`、`navigateTo` 或 `reLaunch` 恢复。
2. 点击结果不明确：先轮询路由，再读 data；不要立即重复点击。
3. data 结构未知：限制深度和数量读取，再用源码搜索缩小字段路径。
4. 宽泛元素查询卡住：恢复 daemon 后停止整树探查，改读路由配置和目标页面源码，再使用精确 selector 或带参数导航。

端口、会话或 daemon 队列异常时按 [diagnostics.md](diagnostics.md) 恢复。

## 执行检查清单

- 做对：用关键请求锁定稳定业务 ID，用源码确认点击路由和副作用，用运行时 data 或组件 data 补充状态，再选择真实点击或等价导航。
- 做对：滚动后读取可见文本或截图，路由变化后重新读取当前页，daemon 重连后先确认动作是否已经完成。
- 做对：启动阶段分别检查 CDP 和 9420；搜索后核对关键请求的 URL、POST data 和响应 ID，而不是只相信界面或路由参数。
- 避免：把接口下标当成视觉顺序，反复尝试无法穿透组件边界的 Page selector，使用大跨度滚动碰运气。
- 避免：在重组件页执行宽泛整树查询，串联多个可能阻塞的动作，或在 daemon 串行队列已被超时请求占用时继续追加命令。
- 避免：无筛选读取整页响应、重复检查已经确认的路由、把 PowerShell 通配符当作 `rg` 路径，以及在启动半成功时切换实例。
